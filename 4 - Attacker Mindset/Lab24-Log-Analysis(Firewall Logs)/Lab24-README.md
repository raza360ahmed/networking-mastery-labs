# Lab 24 - Log Analysis (Firewall Logs)

## Objective

Configure a router to log denied traffic, centralize those logs on a real syslog receiver, and practice basic log analysis techniques to identify patterns in blocked connection attempts. This lab marks the shift from Level 4's attacker-focused labs to Level 5's defender-focused labs: the same kind of traffic generated in earlier labs is now viewed from the logging and detection side.

## Topology

No new nodes required. Kali-Linux-1 was used as both the traffic source and the syslog receiver for this lab, since a dedicated monitoring server was not built into the current topology.

| Node | Role | IP Address |
|---|---|---|
| Kali-Linux-1 | Syslog receiver and traffic generator | 192.168.1.13 |
| R1 | HQ router, logging denied traffic | 192.168.1.1 |

## Configuration

### Syslog receiver (Kali)

Enabled UDP syslog reception in rsyslog, which is disabled by default:

```
module(load="imudp")
input(type="imudp" port="514")
```

```bash
sudo systemctl restart rsyslog
sudo systemctl status rsyslog
```

### Router logging and firewall rule (R1)

```
logging host 192.168.1.13
logging trap informational
service timestamps log datetime msec
access-list 150 deny tcp any any eq 23 log
access-list 150 permit ip any any
interface FastEthernet0/1
 ip access-group 150 in
```

This configuration points R1's log output at Kali, timestamps every log entry, and builds an access list that denies and logs any Telnet (TCP port 23) traffic entering R1's LAN interface. Telnet was chosen deliberately as the blocked protocol, connecting back to Lab 20, where Telnet's plaintext credential exposure was demonstrated directly.

## Tests Performed

1. Confirmed rsyslog was active and listening for remote UDP syslog input on Kali.
2. Generated multiple Telnet connection attempts from Kali toward R1 to trigger the deny rule repeatedly.
3. Confirmed each attempt produced a distinct, timestamped log entry received on Kali via `tail -f /var/log/syslog`.
4. Counted total rule hits using `grep "list 150" /var/log/syslog | wc -l`.
5. Attempted frequency analysis by source address using `grep -oP 'src \K[0-9.]+' | sort | uniq -c | sort -rn` to identify which source triggered the rule most often.
6. Checked timestamp consistency between the router and the syslog receiver using `show clock` on R1 and `date` on Kali.

## Observations

All logged deny events originated from 192.168.1.13, since Kali was used as both the traffic generator and the log receiver in this lab. In a production environment, the source address in these log entries would instead identify a genuinely separate host attempting to reach the blocked service, and the frequency analysis technique becomes far more meaningful when multiple distinct sources are present in the log data.

Each log entry followed the same consistent format:

```
%SEC-6-IPACCESSLOGP: list 150 denied tcp <source>(<port>) -> 192.168.1.1(23), 1 packet
```

This confirmed the access list was correctly denying and logging every matching connection attempt, with distinct source ports on each attempt indicating separate connection tries rather than a single retried session.

## Key Learning

- Logging configuration alone is not analysis. A firewall that logs every denied packet produces no value until someone reviews the log for patterns, repeated activity, or volume.
- The `sort | uniq -c | sort -rn` pattern used to rank source addresses by frequency is a simple, manual version of the same triage logic that a SIEM automates at scale. Learning to do this by hand with `grep` and standard Unix tools builds an understanding of what a SIEM is actually doing underneath its dashboards.
- A single denied connection attempt is normal background noise on any network. Repeated attempts against the same blocked port, especially at regular intervals, are a stronger signal of automated or scripted activity rather than incidental traffic.
- Consistent timestamps between the device generating logs and the receiver storing them are a prerequisite for any real correlation work. This lab confirmed R1 and Kali's clocks were aligned before treating the log timestamps as reliable.
- This lab closes the loop on Level 4: traffic generated by earlier reconnaissance and exploitation labs is, for the first time, being observed from the defender's side of the same event.
